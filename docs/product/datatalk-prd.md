# DataTalk 产品说明文档

## 1. 文档目的

本文档用于定义 `DataTalk` 的产品定位、阶段目标、核心能力边界与后续演进方向，作为当前项目后续设计、研发、接口、数据模型和页面实现的统一参考。

从本文件落地开始，项目默认围绕 `DataTalk` 的目标推进，避免再次回到传统 BI 配置式产品思路。

## 2. 产品名称

- 产品名称：`DataTalk`
- 产品定位语：用对话完成报表开发

## 3. 产品愿景

`DataTalk` 是一个 AI 原生的 SaaS BI 开发平台。  
用户不需要学习传统 BI 工具中复杂的数据集、维度、指标、图表配置流程，只需要通过自然语言描述需求，系统即可帮助用户完成报表开发、修改、复用与分享。

长期目标不是做一个“更简单的 BI 页面配置器”，而是做一个围绕数据资产生产、复用、共享与订阅的智能化平台。

## 4. 要解决的问题

传统 BI 工具的问题主要集中在以下几个方面：

1. 学习成本高  
用户需要理解数据集、字段建模、维度指标、可视化组件、筛选器、权限等大量专业概念。

2. 报表开发链路长  
即使是一个简单报表，也往往需要先接数据源、建数据集、配字段、选图表、调样式，再进行发布。

3. 复用能力弱  
报表结构、布局、样式、数据逻辑和 API 往往分散存在，无法像“资产”一样被发现、复用和二次开发。

4. 协作效率低  
团队内部共享靠人工传递，缺少统一的共享、订阅、模板化机制。

## 5. 产品定位

`DataTalk` 的核心不是“报表查看系统”，而是“对话式 BI 开发系统”。

它面向三类价值：

1. 降低门槛  
把传统 BI 的专业操作压缩为自然语言交互。

2. 提高效率  
让报表从“配置式生产”转为“对话式生成 + 可视化微调”。

3. 形成资产生态  
未来支持报表、数据集、API、模板、布局结构等资源的共享、订阅和再创作。

## 6. 目标用户

### 6.1 第一阶段核心用户

- 业务分析人员
- 运营人员
- 产品经理
- 有报表需求但不熟悉 BI 工具的中后台用户

### 6.2 后续扩展用户

- 数据分析师
- 数据开发/BI 开发人员
- 企业管理员
- 模板创作者与数据资产共享者

## 7. 核心产品原则

1. AI 优先  
所有关键流程优先通过对话触发，而不是让用户先学习复杂配置。

2. 结果优先  
用户要的是“得到报表”，不是理解 BI 内部实现细节。

3. 渐进展开  
默认隐藏数据集、字段映射、图表参数等复杂细节，仅在必要时向高级用户展开。

4. 可复用优先  
报表、数据集、API、模板、布局都应被视为可沉淀、可共享的资产。

5. SaaS 平台化  
从一开始按多租户、权限、资源隔离、共享机制的方向设计。

6. 标准接口优先  
所有业务能力统一通过标准 REST API 暴露，方便前端、多端与外部工具联调。

## 8. 一期 MVP 目标

### 8.1 MVP 定义

一期 MVP 的核心目标是：

**让用户通过一句或几句自然语言，在系统中直接完成报表开发。**

用户不需要显式经历传统 BI 工具中的以下流程：

- 手工配置数据集
- 手工区分维度与指标
- 手工挑选图表组件
- 手工拼接筛选与分组逻辑
- 手工搭建报表页面结构

系统需要在 AI 对话过程中自动理解用户意图，并输出可预览、可继续修改的报表结果。

### 8.2 MVP 必须具备的能力

1. 对话式创建报表  
用户输入自然语言需求，系统生成报表草案。

2. 对话式修改报表  
用户可以继续通过对话调整图表、字段、统计方式、筛选条件、布局和标题文案。

3. 报表预览  
生成后的报表要有清晰的结果页或工作区视图，方便用户直接确认结果。

4. 结果可保存  
用户可将当前报表保存为资源，便于后续继续编辑。

5. 报表目录管理  
支持基本的报表组织方式，便于用户管理自己的成果。

6. 多租户基础能力  
保证不同租户之间的用户、报表和资源隔离。

### 8.3 MVP 暂不追求的能力

以下能力不是一期 MVP 的重点，可先控制复杂度：

- 完整的传统 BI 可视化配置面板
- 复杂拖拽式仪表盘编辑器
- 多人协同编辑
- 跨租户公开市场
- 完整模板商城
- 高级数据建模工作台

## 9. MVP 典型用户场景

### 场景 1：一句话生成销售报表

用户输入：

“帮我做一个最近 30 天各区域销售额趋势图，再加一个品类占比图。”

系统输出：

- 自动识别数据来源
- 自动理解时间范围、统计口径、维度与指标
- 自动选择合适图表
- 自动生成一个可预览的报表页面

### 场景 2：继续修改现有报表

用户输入：

“把区域改成省份，趋势图改成按周统计，再加一个订单数指标卡。”

系统输出：

- 基于已有报表上下文做增量修改
- 保留原有结构的可复用部分
- 更新预览结果

### 场景 3：沉淀为可复用资源

用户完成报表后，可以：

- 保存到指定目录
- 标记用途
- 后续继续编辑
- 为未来共享与模板化能力预留基础

## 10. 后续演进方向

### 10.1 发现模块

后续新增“发现”模块，用于资源流通和能力复用。

可被发现和流通的资源包括：

- 报表
- 数据集
- API
- 仪表盘
- 布局结构
- 模板

核心能力包括：

1. 资源发布  
用户可将自己的资源共享出来。

2. 资源发现  
用户可浏览、搜索、筛选别人共享的资源。

3. 资源订阅  
用户可订阅可复用资源，并在自己的空间中使用。

4. 二次开发  
用户可在共享资源或模板的基础上继续修改，而不是从零开始。

### 10.2 模板能力

后续重点建设模板体系，覆盖：

- 仪表盘模板
- 报表结构模板
- 页面布局模板
- 样式主题模板
- 行业解决方案模板

模板的目标不是只复用“外观”，而是复用：

- 结构
- 样式
- 组件布局
- 字段映射规则
- 常见分析逻辑

### 10.3 资产化平台

长期看，`DataTalk` 要从“AI 生成报表”升级为“数据资产生产与流通平台”。

资产化对象包括：

- 报表资产
- 数据集资产
- 查询/API 资产
- 模板资产
- 分析方法资产

## 11. 产品结构建议

结合当前目标，产品建议逐步演进为以下模块：

1. 工作台 / Workspace  
用户进入系统后的主入口，展示最近资源、推荐动作和当前状态。

2. AI 开发台 / Talk Workspace  
核心区域，用户通过对话创建和修改报表。

3. 报表中心 / Reports  
管理当前租户下的报表资源，支持目录、检索、预览和编辑入口。

4. 发现 / Discover  
浏览和订阅共享资源。

5. 模板中心 / Templates  
查看并复用各类模板。

6. 数据源与资源管理  
维护数据源、数据集、API 等底层资源。

7. 成员与权限  
管理租户成员、角色与资源权限。

## 12. 核心对象定义

为便于后续研发统一认知，建议重点围绕以下核心对象建模：

### 12.1 Tenant

租户，SaaS 隔离的基础单位。

### 12.2 User

租户内用户，拥有角色与资源权限。

### 12.3 Data Source

数据源，连接数据库、接口或其他外部数据系统。

### 12.4 Dataset

可供 AI 理解和报表使用的数据语义层对象。  
在 MVP 中可以先弱化其显式配置，但后端仍需要有统一抽象。

### 12.5 Report

报表资源，是一期 MVP 的核心产物。

### 12.6 Conversation

用户与 AI 的交互上下文，驱动报表创建与修改。

### 12.7 Template

可复用的结构、布局、样式或分析方案载体。

### 12.8 Shared Resource

进入发现模块后可被发布、浏览、订阅的资源统一抽象。

## 13. 关键产品流程

### 13.1 MVP 主流程

1. 用户进入工作台
2. 发起一个报表开发对话
3. 输入自然语言需求
4. 系统解析意图并生成报表草案
5. 用户在预览区确认结果
6. 用户继续通过对话修改
7. 用户保存报表到目录

### 13.2 后续扩展流程

1. 用户创建并保存资源
2. 选择是否共享
3. 其他用户在发现模块浏览资源
4. 用户订阅或克隆资源
5. 在原资源基础上继续二次开发

## 14. 当前项目的研发导向调整

基于本次产品定位，当前项目后续研发建议遵循以下方向：

1. 页面中心从“管理台”转向“AI 开发台”  
工作区应逐步从传统后台信息看板，演进为以对话和结果预览为核心的主工作界面。

2. 报表中心从“静态管理”转向“资源管理”  
不仅管理报表目录，还要为后续共享、订阅、模板化做准备。

3. 数据层设计保留 AI 语义抽象  
即使前端不显式暴露数据集配置，后端仍要为数据源、数据集、字段语义、报表配置保留标准模型。

4. 所有业务能力优先沉淀为 REST API  
避免把关键逻辑绑死在页面层，便于后续对接外部系统和多端能力。

5. 明确区分“用户可见复杂度”和“系统内部复杂度”  
对用户隐藏复杂概念，不代表后端不建模；系统内部仍需保持结构化设计。

## 15. 成功指标建议

一期 MVP 可优先关注以下指标：

1. 首次报表生成成功率
2. 从输入需求到看到首版报表的平均时长
3. 报表二次修改成功率
4. 报表保存率
5. 用户 7 日内重复创建报表的活跃度

二期可进一步关注：

1. 共享资源发布量
2. 资源订阅量
3. 模板使用率
4. 二次开发转化率

## 16. 当前结论

`DataTalk` 的第一性目标已经明确：

**让用户用对话代替传统 BI 配置过程，直接完成报表开发。**

后续一切功能设计都应优先回答两个问题：

1. 这是否让“对话式开发报表”更简单、更直接？
2. 这是否让报表、数据集、API、模板等资源更容易沉淀和复用？

如果答案都是否定的，则不应优先进入当前开发主线。
