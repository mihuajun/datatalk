# BI Metric Knowledge

你负责让当前报表优先复用租户已确认的指标口径，并把本轮经过确认和验证的新口径提交为候选。

## 工作流程

1. 开始实现前调用 `search_metric_knowledge`，每个业务指标分别检索。
2. 返回 `reuse` 时，保留已有公式、时间字段、过滤条件、统计粒度和去重规则。
3. 返回 `confirm` 时，停止修改文件，只向用户询问一个最关键的口径分歧。
4. 返回 `create` 时，按需查看数据源 schema；不得猜测表和字段。
5. 所有准备写入真实查询的 SQL 必须先调用 `preview_sql`。
6. 实现完成后调用 `propose_metric_knowledge`，提交本轮实际使用的结构化口径。
7. 用户否定或纠正历史口径时调用 `record_metric_feedback`。

## 候选提交条件

- `confirmed=true` 只用于用户已经明确描述、明确选择，或直接复用 `verified` 指标的情况。
- 新指标缺少公式、时间字段、过滤条件或去重规则中的关键项时，先提问，不得自行补全后提交。
- `sourceRef` 必须指向当前实现，例如 `server.js#handler:sales-summary`。
- mock 数据、页面样式、布局、标题、图表配色和普通数据集 handler 不属于指标知识。
- 工具提交的只是候选；只有 SQL 预览和报表 Git 提交都成功后，服务端才会发布为正式指标。

## 冲突规则

以下差异视为口径冲突，不能静默覆盖：

- 分子或分母不同
- 聚合字段或聚合方式不同
- 下单时间、支付时间、完成时间不同
- 是否排除退款、测试数据或无效状态不同
- 按订单、用户、设备等去重方式不同
- 数据源不同且无法确认语义一致

遇到冲突时说明两个候选的核心差异，让用户选择；未确认前不修改报表数据逻辑。
